Subject: Teal primitive `expr is <type>` bytecode reconnaissance

Findings:
- `BC_ISTYPE` and `BC_ISNUM` are already part of the v2.1 bytecode set at `src/lj_bc.h:87-93`. Their modes are `var, lit` rather than destination-producing opcodes.
- They are guard/check opcodes, not predicates. The x64 VM falls through when the type matches and calls `vmeta_istype` when it does not (`src/vm_x64.dasc:3227-3238`). x86 is the same shape (`src/vm_x86.dasc:3817-3826`). `vmeta_istype` calls `lj_meta_istype` (`src/vm_x64.dasc:991-999`), and that helper performs implicit coercions or raises an argument type error (`src/lj_meta.c:429-438`).
- The operand encoding used by the library generator is reusable: `src/host/genlibbc.lua:77-80` maps `str=5`, `func=9`, `tab=12`, `int=14`, `num=15`; fixup rewrites `CHECK_*` sentinels into `BC_ISTYPE` or `BC_ISNUM` and stores that value in D (`src/host/genlibbc.lua:110-115`). This is visible in generated library bytecode such as `string.len` using `BC_ISTYPE,0,5,0` (`src/host/buildvm_libbc.h:11`) and table checks (`src/host/buildvm_libbc.h:12-29`).
- Library source uses `CHECK_*` only for argument checks, not boolean tests: examples are `CHECK_tab`, `CHECK_func`, `CHECK_int` in `src/lib_table.c:28-43` and `src/lib_table.c:108-139`, plus `CHECK_str` in `src/lib_string.c:34-37`.
- The JIT recorder treats `BC_ISTYPE/BC_ISNUM` as type guards/coercions matching `lj_meta_istype`, then updates the slot's specialized TRef (`src/lj_record.c:2433-2443`). This is useful for narrowing after a known-success branch, but it still is not a false-producing predicate.
- Parser boolean expressions are represented as jump-list expressions. `VJMP` means `info = instruction PC` (`src/lj_parse.c:33-52`). Comparisons emit an `IS*` instruction, emit a following `JMP`, and mark the expression `VJMP` with Teal boolean type (`src/lj_parse.c:876-923`). Existing branch/value materialization turns jump lists into real booleans with `KPRI false/true` (`src/lj_parse.c:587-609`) and condition consumers use `bcemit_branch_t/f` (`src/lj_parse.c:740-795`).
- Current Teal parser scaffolding already has contextual keyword helpers for soft keywords (`src/lj_parse.c:1087-1105`) and primitive type parsing (`src/lj_parse.c:1113-1139`, `src/lj_parse.c:1181-1213`).

Recommendation:
- Do not lower Teal `expr is <type>` directly to existing `BC_ISTYPE/BC_ISNUM`. Failure currently throws or coerces, while Teal `is` must return false.
- For the proper native path, add new predicate comparison bytecodes appended at the end of `BCDEF`, not inserted near `BC_ISTYPE`. Appending preserves all existing v2.1 opcode numbers, so old LuaJIT bytecode remains loadable. A minimal shape is one `BC_ISATYPE` with operands `RA=source`, `D=encoded type`, followed by the standard `BC_JMP`, matching comparison bytecode style. If number and integer need different fast paths, add `BC_ISANUM` / `BC_ISAINT` or encode those cases in the same VM handler.
- Reuse the existing D encoding from library checks: exact primitive type operands are `~LJ_T* + 1`; string uses 5, function 9, table/record-runtime-table 12, integer 14 on dual-number builds, number 15 for the `tvisnumber` test. Keep nil/boolean exact tests either through `BC_ISEQP` when possible or through the same predicate handler using `LJ_TNIL`, `LJ_TFALSE`, and `LJ_TTRUE`.
- In `lj_parse.c`, add `OPR_IS` as a Teal-only soft binary operator, probably at comparison precedence alongside `==`, `<`, etc. Convert `token2binop` to see `LexState` or add a Teal-aware wrapper so `TK_name("is")` is only an operator in Teal mode. The RHS should be parsed with the existing `teal_parse_type`.
- Add `bcemit_iscomp(FuncState *fs, ExpDesc *e, TealTypeDesc rhs)` beside `bcemit_comp`. It should discharge `e`, put the tested value in a register, emit the new predicate-test bytecode, emit `bcemit_jmp(fs)`, and return a `VJMP` `ExpDesc` with `teal_type = TEAL_T_BOOLEAN` and `teal_nil = 0`. Then existing `expr_toreg`, `not`, `and`, `or`, `if`, assignment, and return paths should continue to work.
- Teach the recorder the new opcode by producing a non-throwing guard and side exit for the false case, unlike `BC_ISTYPE` which records a successful check. This is the piece that makes `if x is integer then ... end` useful for later flow narrowing and optimized typed code.
- As a low-risk interim alternative, lower `expr is string` to `type(expr) == "string"` using existing bytecode. `type()` has a fast function and recorder that returns a constant string after specialization (`src/vm_x64.dasc:1217-1230`, `src/lj_ffrecord.c:220-230`). This avoids bytecode changes, but it is not the tight native predicate path.

Risks:
- `integer` is exact only with `LJ_DUALNUM`. `src/host/buildvm_lib.c:179-181` rewrites int checks to number checks for non-dual-number library bytecode. Teal `is integer` needs an explicit policy for non-dual-number builds.
- Adding a new opcode requires updating every VM backend, generated `jit/vmdef.lua`, bytecode mode metadata, disassembly expectations, and the recorder. Appending the opcode avoids old-opcode renumbering, but new bytecode will be TealJIT-specific.
- Reusing `BC_ISTYPE` by changing its failure behavior would break library argument checks and is not acceptable.

Recommended tests:
- Parser/runtime: `assert("x" is string)`, `assert(not ("x" is integer))`, `assert(nil is nil)`, `assert(true is boolean)`, and use `is` inside `if`, assignment, return, `not`, `and`, `or`.
- Bytecode compatibility: build/load an existing v2.1 bytecode dump and verify opcode numbering did not change. Also dump a TealJIT chunk with the new op and verify disassembly names/modes are sane.
- JIT: run a hot loop with `if x is integer then sum = sum + x end` and inspect `-jdump` for an efficient type guard/side exit rather than a `type()` call path.
