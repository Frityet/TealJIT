# Native Teal support reference note

Timestamp: 2026-06-29 18:28:04 UTC
Repo commit: 9d145d2c
Reference scope: `tl/` only. This note paraphrases behavior and cites paths; it does not copy Teal reference code.

## Implementation posture

Teal is a typed Lua dialect whose generated output is ordinary Lua. Native TealJIT support should separate three concerns:

1. Accepting Teal syntax in the lexer/parser.
2. Erasing or lowering type-only constructs to LuaJIT-compatible runtime code.
3. Optionally reproducing Teal's static type checker and diagnostics.

The smallest useful native path is parser support plus faithful erasure/lowering. A full `tl check` equivalent is much larger because `is`, `where`, macroexp, interface inheritance, arity pragmas, total variables, and declaration-file/global-env loading are type-system features, not just syntax.

## Grammar surface to account for

Teal extends Lua statements with typed `local`/`global` declarations, `record`, `interface`, `enum`, `type`, and `macroexp` declarations. Function declarations can carry generic type variables, typed parameters, optional parameter markers, return type lists, and typed varargs. Table fields can carry field type annotations.

Types include primitives, `any`, `nil`, `integer`, arrays, maps, tuples, function types, nominal paths, generic applications, union types, and `require`-based type imports. Records/interfaces add nested type declarations, record keys including literal-string keys, `userdata`, `metamethod`, array/tuple interfaces, `is` interface lists, and `where` discriminators.

Lexer changes should preserve soft-keyword behavior. The specs show `global`, `type`, `record`, and `enum` can remain ordinary identifiers in non-declaration positions, so globally reserving them would be a compatibility regression. `as` and `is` behave as operators only where expression grammar permits them.

Operator precedence matters: `as` binds very tightly as a postfix cast, while `is` sits between `and` and relational comparisons. The `operator/is` specs include precedence regressions around `or` and `and`.

Teal grammar includes Lua 5.3-style operators such as integer division and bitwise operators. Existing Teal generation can target LuaJIT/Lua 5.1 by lowering compatibility cases; native TealJIT must either implement these operators in the parser/code generator or reject them under a stated compatibility mode.

## Pragmas

Only `--#pragma arity on/off` appears as current pragma behavior in the reference docs/specs. Other `--#` comments are ignored unless they use the pragma form. Invalid pragma names, punctuation in pragma arguments, invalid arity values, and multi-line pragma values are rejected by `tl`.

`arity on` enforces function-call argument counts; optional parameters marked with `?` widen the accepted count. `arity off` treats all function arguments as optional and ignores the `?` marker for arity purposes. Pragmas flow downward into modules loaded while the setting is active, but a required module's setting does not leak back upward into the requiring module.

For a parser-only TealJIT mode, pragmas can remain comments. For native checking, they require per-compilation-unit state and require-time propagation semantics.

## Strict, lax, and nil behavior

`.tl` mode is strict about declarations: a local needs either a type annotation or an initializer from which a type can be inferred. An initializer that provides no value is an error in strict mode. Globals must be declared with `global` unless they come from the standard environment or a configured global environment declaration.

`.lua`/lax mode introduces `unknown`. Untyped locals are allowed and unknown-driven errors are suppressed, but literal values and initialized variables still get inferred types. The reference treats this as gradual typing for Lua files, not as Teal's default.

Nil is intentionally permissive in current Teal. The nil subtyping specs show `nil` assignable to primitives, nominal types, enums, arrays, maps, records, functions, unions, `any`, and `unknown`. Optional parameters are only about omitted call arguments; they do not mean non-optional parameters reject explicit `nil`. There is no strict-nil feature yet.

## Records and interfaces

Records are nominal types. Two records with the same fields are not equivalent unless one is an alias of the other. Plain table literals may initialize a record when their shape matches, but record-to-record assignment follows nominal identity/aliasing rules.

Concrete record declarations can also create runtime tables when the record name is used as a value, as a method container, or through aliases. Type-only local declarations may be elided if never needed at runtime; global type declarations are more conservative and can materialize globals. Native support must preserve this elision/materialization distinction rather than blindly dropping every type declaration.

Record methods/functions are only valid for records and must be resolved in the proper scope. Interfaces are abstract: they can describe fields and functions, and values can have interface type, but the interface itself is not a concrete implementation target.

`is` on declarations is interface/subtyping machinery, not record inheritance. Records cannot inherit implementation from other records. Interfaces can compose multiple interfaces; compatible fields are inherited, incompatible field types are errors, and fields are covariant where the specs cover interface refinement. Array and tuple interfaces propagate through records/interfaces, with warnings or errors for overlapping/incompatible combinations.

`userdata` records/interfaces mark values that cannot be constructed from ordinary table literals. Specs cover duplicate userdata declarations, propagation through interfaces, and rejection of table construction for userdata records.

`where` clauses are discriminator logic used by `is`; the macroexp docs describe them as sugar for an `__is` macro expression. Implementing `is` fully therefore requires either macroexp expansion support or a compatible discriminator-lowering path.

## Annotations and attributes

Type annotations appear after colons in locals, globals, parameters, returns, table fields, and record/interface entries. Optional parameters use `?` on the argument name in named declarations and before the type in unnamed function-type parameter positions.

Variable attributes use Lua 5.4-style angle brackets. Known attributes are `<const>`, `<close>`, and `<total>`. Unknown attributes are syntax errors.

`<const>` is compile-time reassignment prevention for the variable binding, not deep immutability of table contents. `<close>` is only valid for Lua 5.4 generation and should be rejected or explicitly unsupported in a LuaJIT native mode unless TealJIT implements equivalent closing semantics. `<total>` applies only to literal table initialization of maps/records over finite domains; it requires all keys/fields to be explicitly mentioned, accepts explicit nil entries as coverage, and prevents reassignment.

## Casts and `as`

`as` is a compile-time trust cast, not a runtime conversion. It can force enum, function, record, array/map/tuple, and multi-return tuple types. It should erase in generated runtime code, while still affecting static type information.

Multi-return casts use a parenthesized list of target types and are important around dynamic returns such as unpack-style functions. Specs also cover `as` inside table literals and syntax-error behavior for incomplete casts.

Because casts can hide real runtime errors, native support should not add conversion behavior. If type checking is absent, parsing and erasing `as` is the least surprising behavior.

## `is` and flow typing

Expression-level `is` narrows union types in conditionals and selected boolean expressions. The specs cover then/else narrowing, negation, incremental `elseif` narrowing, generic type arguments, while-loop behavior, assignment invalidating a narrowed fact, and known truthy expressions preserving inference.

Runtime generation for `is` is not just `type()` in all cases. Primitive checks can lower to runtime type checks, while record/interface discriminators can involve generated `__is`/`where` logic. Current limitations include unions that cannot be discriminated unambiguously between multiple table-like or string/enum-like alternatives.

For parser-only support, `is` still needs a runtime lowering decision. It cannot simply erase like `as`, because users expect it to produce a boolean expression.

## Macro and macroexp scope

`macroexp` is a restricted inline expression expansion mechanism used for `where`, pseudo-metamethods, and selected record fields. Declarations produce no runtime Lua by themselves. Full local `macro` is broader AST-generation machinery with `!` invocation and quoting/splicing syntax.

Native TealJIT can defer broad macro support, but then it should reject or clearly gate `local macro`, macro calls, and quote/splice forms. `macroexp` is harder to defer if `where` and non-primitive `is` are in scope.

## Suggested implementation order

1. Add a Teal parsing mode that keeps Lua mode unchanged and treats Teal-only keywords as contextual.
2. Parse and skip type syntax everywhere it can occur; erase annotations and `as` casts while preserving expression/statement boundaries and line mapping.
3. Lower runtime-bearing declarations: locals/globals, concrete record tables when used as values, record methods, aliases that must materialize, and global type materialization.
4. Decide the first-class scope for `is`: primitive-only runtime lowering first, then `where`/`__is` and interface-aware checks.
5. Add arity pragma/type-check behavior only after the parser/lowering path is stable.
6. Build conformance tests from the anchor files above using small original fixtures, not copied reference snippets.
