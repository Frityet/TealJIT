## Minimal First Native Slice

Implement parser-owned function signature metadata for local functions, function
expressions assigned to typed locals/record fields, and record functions/methods:

- Capture fixed positional parameters: primitive/record type tag, nilability,
  and whether the parameter was marked optional with `?`.
- Capture a single return type initially, plus explicit zero-return `(): ()` and
  `nil` return distinction. Defer multi-return/vararg returns until tuple work.
- Store signatures on local function variables and on known record fields.
- Parse function-type record fields such as `foo: function(string): integer`.
- For calls to known signatures, check:
  - callee is callable,
  - argument count is between required count and total count,
  - each provided argument is assignable to its parameter type under TealJIT
    strict nil-safety,
  - non-returning `(): ()` calls cannot initialize a value.
- For colon calls, account for the implicit receiver as argument zero/one:
  `obj:method(a)` checks the receiver against the first `self` parameter and
  user arguments against the rest; `obj.method(a)` must include receiver
  explicitly when the field is a method-style function.
- When parsing `function R.foo(...)` or `function R:foo(...)`, create or validate
  the record field signature and give `self` the receiver record shape in colon
  form.
- Keep `--#pragma arity on` behavior as the default. A separate `arity off`
  implementation can come later; strict mode should not silently treat missing
  non-optional parameters as safe.

This slice is parser/checker metadata only. It should not change dumped bytecode
format. It can still improve bytecode later by using known primitive parameter
and return types to avoid conservative runtime paths.

## Risks and Deferred Cases

- Full Teal supports generic functions, type variables, constraints, overload
  intersections, and expected-type-driven inference. First slice should parse
  past or reject these deliberately.
- Varargs, typed named varargs, `T...` return lists, multi-return adjustment, and
  tuple return checking need a broader tuple/value-list representation.
- Function subtyping and assignment compatibility are not just arity equality:
  optional arguments are bivariant in existing specs and should be handled in a
  later function-type lattice pass.
- Record method detection is nuanced. Dot calls can be valid when an explicit
  receiver is supplied, while obvious missing-receiver cases should error.
- Overloaded record functions require selecting a matching signature by arity
  and argument types. A first slice should reject overload redeclarations or
  choose only an exact single signature.
- `--#pragma arity off` is separate from this fork's `strict` pragma. Supporting
  it later requires parser state that is inherited downward into required
  modules but not upward from them.
- Return arity in upstream Teal permits too few values in some cases. TealJIT's
  strict nil-safety may eventually want to be stricter, but that should be an
  explicit fork policy rather than an accidental parser behavior.
