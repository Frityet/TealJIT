## Native probe results

I used the existing x64 `src/luajit` binary only to dump IR; no rebuild was
needed. Because the in-tree `jit.*` modules are not installed globally, set
`LUA_PATH='src/?.lua;;'`.

Constant return:

```sh
LUA_PATH='src/?.lua;;' src/luajit -jdump=irs -e 'jit.opt.start("hotloop=1","hotexit=1") local function f() return 42 end f(); f(); f(); print(f())'
```

Shape:

```text
---- TRACE 1 IR
.... SNAP #0 [ ---- ---- ]
.... SNAP #1 [ ---- ---- +42 ]
---- TRACE 1 stop -> return
```

Finding: a constant-return hot function is almost all snapshot/link plumbing.
It is a good smoke test for `LJ_TRLINK_RETURN`, but not a useful IR expression
lowering test.

Addition return:

```sh
LUA_PATH='src/?.lua;;' src/luajit -jdump=irs -e 'jit.opt.start("hotloop=1","hotexit=1") local function add(a,b) return a+b end add(1,2); add(3,4); add(5,6); print(add(7,8))'
```

Shape:

```text
0001 > num SLOAD #2 T
0002 > num SLOAD #3 T
0003   num ADD   0002 0001
---- TRACE 1 stop -> return
```

Finding: this is the smallest non-empty useful lowering target. It needs stack
slot loads with type checks, numeric `ADD`, result materialization for the
return snapshot, and `LJ_TRLINK_RETURN`.

Numeric for loop:

```sh
LUA_PATH='src/?.lua;;' src/luajit -jdump=irs -e 'jit.opt.start("hotloop=1","hotexit=1") local s=0 for i=1,3 do s=s+i end print(s)'
```

Shape:

```text
0001   int SLOAD #3 CI
0002 > num SLOAD #2 T
0003   num CONV  0001 num.int
0004 + num ADD   0003 0002
0005 + int ADD   0001 +1
0006 > int LE    0005 +3
0007 ------------ LOOP ------------
0008   num CONV  0005 num.int
0009 + num ADD   0008 0004
0010 + int ADD   0005 +1
0011 > int LE    0010 +3
0012   int PHI   0005 0010
0013   num PHI   0004 0009

```

Finding: the first loop subset should cover integer loop counters and numeric
accumulators, but can avoid `ADDOV` if validation scripts use constant small
loop bounds/steps. Negative or variable-step loops also need `LT`/`GE`/`GT`;
constant positive examples need `LE`.

## Smallest useful first lowering subset

Recommended order:

1. Return-link trace with no regular ops: handle `LJ_TRLINK_RETURN` and snapshot
   result materialization using constants (`KINT`/`KNUM`/primitive refs). This
   proves the Wasm module can compile and return through the host contract.
2. Hot function `return a+b`: add `SLOAD`, `KNUM`, `ADD` for `IRT_NUM`, and type
   guard exits. This is the first real IR-to-Wasm expression path.
3. Positive numeric `for` loop: add `KINT`, `CONV` with `IRCONV_NUM_INT`,
   integer `ADD`, signed integer `LE`, `LOOP`, and `PHI`. This is the first real
   loop path.

Concrete minimum whitelist for step 2:

- Constants: `IR_KINT`, `IR_KNUM`, and existing primitive refs from `IR_KPRI`.
- Loads: `IR_SLOAD` for argument/result slots, with `IRSLOAD_TYPECHECK` and
  readonly/inherited modes tolerated.
- Arithmetic: `IR_ADD` for `IRT_NUM`.
- Guards/control: type guards attached to `SLOAD`; return link
  `LJ_TRLINK_RETURN`.
- Ignored/no-code ops: `IR_BASE`, `IR_NOP`, `IR_RENAME`.

Concrete loop extension:

- `IR_ADD` for `IRT_INT` and `IRT_NUM`.
- `IR_CONV` for `IRCONV_NUM_INT`.
- `IR_LE` first; reserve the same compare lowering shape for `IR_LT`, `IR_GE`,
  and `IR_GT`.
- `IR_LOOP` and `IR_PHI` for loop-carried values.

Defer initially:

- `IR_ADDOV`/`IR_SUBOV`/`IR_MULOV`: important for integer arithmetic, but not
  required by the sampled positive numeric-for/addition traces.
- `IR_EQ` and table/function loads (`FLOAD`, `HREFK`, `HLOAD`): these appear in
  stitched traces that call `print` or specialize a callee from inside another
  trace, but they are avoidable for the first isolated arithmetic/function-entry
  validation.
- `IR_RETF`: needed for lower-frame return guards, but not for the minimal hot
  function-entry `-> return` traces above.

## Wasm emitter implications

The current emitter has `local.get/set/tee`, `block`, `loop`, `br`, `br_if`,
`return`, and constants. Add at least:

- Numeric ops: `i32.add`, `f64.add`, maybe `i32.sub` soon after.
- Comparisons: `i32.le_s`, plus `i32.lt_s`, `i32.ge_s`, `i32.gt_s`.
- Conversion: `f64.convert_i32_s`.
- Memory: enough `i64`/`f64` loads and stores to read/write TValue slots from
  the `base` pointer. On wasm64 the address value is i64 even though the load
  opcodes are the standard memory opcodes.
